# AirNote 版本管理流程

本文件规定每日开发记录如何在负责人批准后汇总为正式版本变化。

## 两类记录

### 每日进度

- 路径：`docs/progress/YYYY-MM-DD.md`。
- 触发：任务实际修改了项目受版本控制文件。
- 内容：完成事项、功能 ID、关键文件、参数、测试、限制、下一步和 Git 状态。
- 含义：记录开发事实，不代表形成正式版本。

### 成立版本

- 触发：负责人明确表示某个版本成立、批准发布或给出等价授权。
- 内容：汇总自上一个成立版本以来的每日进度，形成可追踪的版本变化。
- 限制：未获批准前，不更新版本号，不创建 `CHANGELOG.md` 条目、版本说明、Git 标签或 GitHub Release。

## 版本成立后的自动记录步骤

1. 检查工作区、功能 ID、自动测试和人工验收结果。
2. 汇总相关每日进度，区分已完成、已验证、未验证和延期内容。
3. 创建或更新 `CHANGELOG.md`，按“新增、变更、修复、安全、已知限制”分类。
4. 按批准内容更新 `package.json` 版本号，并同步锁文件。
5. 创建 `docs/releases/<version>.md`，记录范围、功能 ID、关键变化、验证证据、兼容性和限制。
6. 再次核对产品需求文档与产品边界文档，确认没有把 P2、未验收或越界内容写成已交付。
7. 仅在用户明确授权后执行 Git 提交、标签、推送或 GitHub Release。

## 版本号建议

- 技术尖峰或里程碑候选可使用预发布标识，例如 `0.1.0-m0.1`。
- 首个完整 P0 MVP 可使用 `0.1.0`。
- 向后兼容的修复增加修订号；新增兼容能力增加次版本号。
- 实际版本号以负责人批准为准，不由工具自行决定。

## 提交信息建议

提交标题保持简短，正文写明：

- 关联功能 ID；
- 用户可见变化；
- 关键技术决策或参数变化；
- 执行的测试与结果；
- 已知限制和未验证事项。

版本成立不自动等于允许提交或推送。除非负责人在同一指令中明确批准，否则仍需在 Git 操作前单独确认。
